一、刷机备份

强烈建议刷机之前先把当前的分区进行备份，后面随时可以恢复

背景知识学习

U-boot15（armv8）启动流程（基于展锐平台）_展锐 开机流程-CSDN博客

展锐UDX710：u-Boot 初始化流程分析_udx710开发软件-CSDN博客

天翼一号2021搭载安卓10，soc是紫光展锐虎贲t7510，对应的主板也叫做ud710-7h10-ctcc，其中ctcc就是中国电信，电信定制机的意思，进入原厂的rec可以看到这个ud710-7h10-ctcc型号。

目前有原厂的360os魔改的广告系统，有flyme，有AOSP10，flyme和aosp10据说是开发时工程机上的系统

1.u2s模式刷机工具

SpreadTrum u2s diag，是一个类似于 MTK 的深度刷机端口，高通的 9008 端口，麒麟的 COM1.0 端口的深度刷机端口。u2s 端口一般可以干这些事情：

  • 救砖

  • 刷系统

  • 重新分区

  • 备份系统

首先安装SPRD U2S DIAG所需驱动，请使用搜索引擎查找

天翼一号进入u2s模式：按住设备电源键不动 设备黑屏后马上按住所有按键不动（音量+- 电源键）

u2s刷机工具有两种，一种是官方的SPD Flash Tool，SPD Flash Tool是适用于用于展讯芯片组手机或平板设备固件的刷新工具。目前有三款不同的下载工具，适用于不同的使用场景。详情见(新手教程：SPD Flash Tool使用介绍及刷入多亲2Pro的PAC固件救砖_安卓手机_什么值得买)。

  1. FactoryDownload (用于PCBA阶段生产下载。该工具会初始化PhaseCheck、ProdNV分区、擦除NV参数、预写SN号)

  2. UpgradeDownload (用于PCBA或者手机整机的软件升级，升级前会检查校准标志位是否置pass，否则无法进行升级。该工具的主要特点是对NV参数进行强制备份、不会初始化PhaseCheck、ProdNV分区)

  3. ResearchDownload (用于研发开发调试。支持读写Flash分区，支持NV参数、PhaseCheck、ProdNV分区的备份，支持对下载文件打包等功能。但此工具默认不初始化ProdNV、PhaseCheck分区)。备份教程(使用ResearchDownload为展讯机型提取镜像 - ZH-XiJun’s GitHub pages)。备份的文件是很多个bin和img文件，可以参考这个教程(How to use research download tool to create Unisoc / Spreadtrum pac file)打包成pac。

    ！注意，发现ResearchDownload备份分区会相比spd_dump少十多个，所以不建议使用了

还有一种是spd_dump，是民间大神TomKing062开发的，详细介绍(SPD Dump使用指南！ – 摸鱼真君不摸鱼的小站)，下载地址可以去大神的github官网下载解锁bootloader的文件Releases · TomKing062/CVE-2022-38694_unlock_bootloader，里面自带的有适用于天翼一号的spd_dump

二、构建ud710 BSP开发环境

参考这个教程如何为 UD710 编译 Chipram – LinearTeam，去github下载ud710的BSP源码，这个源码可以生成splloader和uboot（正常开机用的），也就是fdl1.bin和fdl2.bin（u2s刷机用的），这里device文件夹里面没有天翼一号2021的设备树，有的是科大讯飞平板的一些设备树，这些设备也是用的t7510，有些主板也是ud710_7h10，编译测试了一下，ud710_7h10_ctcc生成的fdl1和fdl2能用(要要用25年7月的ud710_tyyh2021.zip解锁文件跑，最新的ud710_tyyh2021.zip无法运行服了)，也就是内存有一些差异的，但是后面的emmc等设备是兼容的

根据教程安装ubuntu18.04.6 LTS并且安装一些包，根据要求就可以编译

安装Device Tree Compiler (DTC)工具，这个工具应该是linux通用的

Device Tree Compiler (DTC) 是一个用于将设备树源码（DTS 或 DTSI 文件）编译为二进制格式（DTB 文件）的工具，广泛应用于 Linux 内核开发和嵌入式系统中。设备树的主要目的是将硬件描述与内核源码分离，从而提高系统的可移植性和灵活性。

经过群里大佬提醒，原理是recovery-from-boot.p生成 Android recovery 镜像 | Hexo，开机检查rec哈希不对就会自动触发生成新的rec，服务在init.rc里面

1
2
3

service flash_recovery /system/bin/install-recovery.sh
    class main
    oneshot
字段含义
service flash_recovery定义一个名为 flash_recovery 的服务
/system/bin/install-recovery.sh启动时执行的脚本路径
class main属于 main 类，会在系统正常启动阶段被触发执行
oneshot只执行一次，不会常驻后台，执行完就退出

install-recovery.sh 一般是 OTA 升级或厂商预置的脚本，典型操作包括：

  1. 读取 /system/recovery-from-boot.p（一个补丁文件）
  2. 用 applypatch 工具，将当前内核（boot）分区打补丁，生成官方 Recovery 镜像
  3. 将生成的 Recovery 写入 Recovery 分区

5. 修复循环重启进入twrp

刷完twrp后循环进入twrp，刷入官方的rec后重启进入rec，选择重启后进系统，先恢复过来，先不管了

进一步修复twrp循环重启

1
2

dd if=/dev/zero of=/dev/block/by-name/misc bs=1 count=32
reboot

在twrp终端里面一个一个敲真折磨，但是重启后就正常进系统了，现在也好了

不想折磨的话就进spd_dump擦除misc分区再重启就进系统了

1
2

e misc
reset

原理是 misc 分区中的一条“重启到 Recovery”指令没有被清除。Bootloader 每次启动时读到这条指令，就会再次进入 Recovery，形成循环

核心原理：BCB 结构

misc 分区是 Android 系统中一个用于系统与 Bootloader 通信的专用区域。其最关键的部分，在起始的 2KB 空间里，存放着名为 bootloader_message 的结构体。这个结构体定义在 AOSP 的源码中，主要包含三个字段：

  • command[32]: 核心指令字段。Bootloader 在启动时会检查此字段，并根据其值决定启动模式。
  • recovery[768]: 用于向 Recovery 模式传递额外参数，例如在重启后自动执行刷机脚本。
  • status[32]: 用于 bootloader 向系统返回操作状态（现已较少使用）

static int input_event_haptics_fd = -1;
static unsigned long input_event_haptics_uses_rumble = 1;
static signed short input_event_haptics_effect_id=-1;
static int input_event_ff_open(const char *input_dev_path)
{
    if (input_event_haptics_fd >= 0)
        return input_event_haptics_fd;

    int fd = open(input_dev_path, O_RDWR | O_CLOEXEC);
    if (fd < 0){
        LOGI("Cannot open file %s\n", input_dev_path);
        return -1;
    }

    unsigned long ff_bitmask[NBITS(FF_MAX)];
    memset(ff_bitmask, 0, sizeof(ff_bitmask));
    if (ioctl(fd, EVIOCGBIT(EV_FF, sizeof(ff_bitmask)), ff_bitmask) < 0) {
        close(fd);
        LOGI("Cannot ioctl file %s\n", input_dev_path);
        return -1;
    }

    if (test_bit(FF_CONSTANT, ff_bitmask) || test_bit(FF_RUMBLE, ff_bitmask)) {
        input_event_haptics_fd = fd;
        input_event_haptics_uses_rumble = !test_bit(FF_CONSTANT, ff_bitmask);
        return input_event_haptics_fd;
    }
    LOGI("unsupported Force Feedback ff_bitmask\n");
    close(fd);
    return -1;
}
static int input_event_ff_vibrate(int timeout_ms)
{
    if (input_event_haptics_fd < 0){
        LOGI("wrong fd %d\n",input_event_haptics_fd);
        return -1;
    }

    if (input_event_haptics_effect_id>=0 &&ioctl(input_event_haptics_fd, EVIOCRMFF, input_event_haptics_effect_id) == -1) {
        LOGI("fail to remove effect \n");
    }

    struct ff_effect effect;
    memset(&effect, 0, sizeof(effect));
    effect.id = -1;
    effect.replay.length = timeout_ms;
    effect.replay.delay = 0;

    if (input_event_haptics_uses_rumble) {
        effect.type = FF_RUMBLE;
        effect.u.rumble.strong_magnitude = 0x7fff;
        effect.u.rumble.weak_magnitude = 0x7fff;
    } else {
        effect.type = FF_CONSTANT;
        effect.u.constant.level = 0x5fff;
    }

    if (ioctl(input_event_haptics_fd, EVIOCSFF, &effect) < 0){
        LOGI("fail to regist effect \n");
        return -1;
    }

    input_event_haptics_effect_id = effect.id;

    struct input_event play;
    memset(&play, 0, sizeof(play));
    play.type = EV_FF;
    play.code = input_event_haptics_effect_id;
    play.value = 1;
    if (write(input_event_haptics_fd, &play, sizeof(play)) <0){
        LOGI("fail to play effect \n");
        return -1;
    }
    return 0 ;
}

8.修复内部存储乱码

先明确 FBE 下两个关键存储区域：

  • DE（Device Encrypted，设备加密）：对应目录 /data/user_de/0/。此类数据在用户解锁设备前即可访问（如闹钟、锁屏服务）。其解密密钥由 Keymaster 生成并存储在硬件信任区（TEE），不依赖用户锁屏密码。
  • CE（Credential Encrypted，凭据加密）：对应目录 /data/user/0/ce/。此类数据（如联系人、短信、个人应用数据）必须在用户输入锁屏密码（PIN/图案/密码）并通过验证后才能解密。

keystore_auth 的出现，是为了绕过 Android keystore 服务的一个关键安全限制。keystore 服务会检查调用者的 UID（用户 ID），并拒绝让 root 用户添加身份验证令牌（auth tokens）TWRP 以 root 权限运行，无法直接调用 keystore 服务完成解密。同时，解密流程又必须通过 keystore 服务进行，这就形成了一个死结。keystore_auth 的解决方案是创建一个以普通系统用户（system）身份运行的代理服务-。这个服务拥有向 keystore 服务添加令牌的权限，从而绕过了 root 用户的权限限制。

错误码 -62 在 Keymaster 中通常对应 KM_ERROR_KEY_REQUIRES_UPGRADE，这个错误通常发生在 Android 系统更新（特别是安全补丁级别变化）后-。为了安全，Keymaster 会将密钥与系统版本绑定。当 TWRP 等恢复环境尝试使用这些密钥时，如果其“声明的”系统版本与密钥绑定的版本不匹配，Keymaster 就会返回此错误，要求先升级密钥才能使用

解决这个问题的核心思路是让 TWRP 能够正确模拟或适配当前系统的 Keymaster 环境

需要在编译 TWRP 时，让它的版本信息与设备当前系统保持一致。

  1. 获取系统版本信息：从设备当前系统的 /system/build.prop 文件中，找到以下两个关键属性：

    • ro.build.version.security_patch (安全补丁日期)
    • ro.build.version.release (Android 版本)

  2. 在 TWRP 编译中设置：在 TWRP 设备树的 BoardConfig.mk 文件中，添加或修改以下变量，填入你获取到的值：

    1
2
3
4

    # 例如：PLATFORM_SECURITY_PATCH := 2025-11-01
PLATFORM_SECURITY_PATCH := <你设备的安全补丁日期>
# 例如：PLATFORM_VERSION := 15
PLATFORM_VERSION := <你设备的Android版本号>

    这能让 TWRP 在请求解密时，向 Keymaster 声明一个与系统匹配的版本，从而避免触发升级流程

9. 修复fastbootd模式

目前twrp在重启选项中有重启进入fastboot模式和重启进入bootloader两个选项，但是其实是一回事，都是重启进入了uboot的fastboot模式，而我们一般说的fastbootd模式其实是twrp在recovery环境下启动fastbootd这个守护进程模拟的fastboot模式，

fastboot模式是一个系统重启命令（相当于 reboot bootloader）。它会彻底退出 TWRP 内核，让手机硬件复位，并加载芯片厂商（如高通/展锐）底层的 Bootloader 固件（Aboot / U-Boot）。
